# AI Agent Session Center

Localhost dashboard (port 3333) that monitors AI coding agent sessions (Claude Code, Codex) via hooks. Sessions are visualized as 3D robot characters in an interactive cyberdrome. Supports SSH terminals, team/subagent tracking, prompt queuing, workspace snapshots, and session resume.

## Tech Stack

| Layer | Technology |
|-------|-----------|
| Backend | Node.js 18+ (ESM), Express 5, ws 8, tsx |
| Frontend | React 19, Three.js / @react-three/fiber, Zustand 5, Vite 7 |
| Desktop | Electron 34, electron-builder 25 |
| Terminal | node-pty, server-owned, streamed over WebSocket (Electron's IPC PTY host has no renderer caller) |
| Hooks | Bash script → JSONL file-based MQ (HTTP POST fallback) |
| Persistence | SQLite / better-sqlite3 (server) + IndexedDB / Dexie (browser) |

## Architecture

### Data Flow

```
AI CLI (Claude/Codex)
  → hooks/dashboard-hook.sh (jq enrichment, ~2-5ms)
  → /tmp/claude-session-center/queue.jsonl (atomic append ~0.1ms)
  → server/mqReader.ts (fs.watch + debounce)
  → server/hookProcessor.ts (validate + route)
  → server/sessionStore.ts (state machine + coordinator)
  → server/wsManager.ts (broadcast to browsers)
  → Browser (Zustand stores → React render)
Total: 3-17ms end-to-end
```

## Session State Machine

```
SessionStart       → idle       (Idle animation)
UserPromptSubmit   → prompting  (Walking + Wave, seeks desk)
PreToolUse         → working    (Running, tool-specific animation)
PostToolUse        → working    (stays)
[timeout]          → approval   (Waiting — needs tool approval)
[timeout]          → input      (Waiting — needs user answer)
PermissionRequest  → approval   (reliable signal, overrides heuristic)
Stop               → waiting    (ThumbsUp/Dance)
[2min idle]        → idle
SessionEnd         → ended      (Death — kept in memory)
```

## Key Invariants

- **Never mutate session objects** — always spread/new Map
- **Never use Zustand inside R3F Canvas** — causes React Error #185; all store reads in DOM layer, data flows via props
- **The 3D Canvas must never run at `frameloop="always"` unconditionally.** Electron disables `MacWebContentsOcclusion`, so — unlike a browser tab — a window buried behind another app is *not* reported hidden and keeps its rAF loop running: a 60 fps scene with shadows + antialiasing + 8 `useFrame` sites × session count, rendering forever in the background. `frameloop` is gated by [`resolveFrameloop(visible, focused)`](src/lib/sceneFrameloop.ts) → `never` / `demand` / `always`. **`demand` only works with the `FramePump`** (`invalidate()` on a `UNFOCUSED_FRAME_MS` interval): the robot walk cycles and particle drift are continuous `useFrame` animations, not state-change redraws, so a bare `demand` freezes the scene mid-stride. Keep `sceneFrameloop.ts` import-free (no Three.js) — it is read from the DOM layer.
- **Never call a process probe synchronously on the event loop.** `hasChildProcesses` (approval detection) runs `pgrep -P <pid>` once per approval-timer expiry *per session*; as `execFileSync` it blocked the one loop that also serves WS broadcast, terminal relay and hook processing, so a single session's probe froze every session — worse the busier the box, since `pgrep` scales with the process table. It is `execFile` + `promisify` now, and because the `await` yields, the timer **must** re-read the session afterwards and bail unless it is still `working` with a `pendingTool` (else a `PostToolUse` that landed mid-probe gets overwritten).
- **A `fitAddon.fit()` reading that's non-zero is not proof it's final — and this has cost three separate debugging passes to relearn.** `MIN_SANE_COLS` (`useTerminal.ts`) rejects near-zero measurements (a fully hidden container), but a remount (e.g. DetailTabs' PROJECT split/stacked toggle moving the terminal to a new JSX parent, or `reparent()`'s fullscreen toggle) can attach mid-reflow and measure a small-but-plausible width — 20-30 cols — that clears the threshold easily and is indistinguishable from a genuinely narrow terminal by value alone. Sending it to the PTY is **permanent**: Claude Code hard-wraps its own output at that column count, and xterm can re-flow only its *own* soft wraps, never PTY-emitted hard newlines — the corrupted scrollback never heals, even once the container reaches its real width. `verifySettled` is the fix that actually closes this (a value check never can): re-measure one frame later and only send if two consecutive readings agree; skipping is always safe, sending a premature value is not. It gates the two call sites confirmed as remount-triggered (the initial attach fit, `forceCanvasRepaint`'s post-`reparent` resize); four other `fit()` sites in the same file remain unguarded even by a basic size check and are the most likely next place this resurfaces.
- **A narrow device renders at the PTY's width — it must NEVER resize the PTY to its own.** A PTY spawns at 120 columns; a phone in portrait measures ~49. Pushing 49 to the PTY is the same one-way corruption as the `fitAddon.fit()` hazard above (Claude Code hard-wraps its own output at `process.stdout.columns`, and xterm can re-flow only lines *it* wrapped), except the trigger is a *correct* measurement of a genuinely narrow screen — so neither `MIN_SANE_COLS` nor `verifySettled` can catch it: both exist to reject *wrong* readings, and 49 is right. The server already blocks a spectator (`holdsControl` gates `TERMINAL_RESIZE` in [`wsManager.ts`](server/wsManager.ts)), which left one hole: a phone that **takes control in order to type** would reflow the Mac's scrollback as a side effect nobody asked for. [`terminalGeometry.ts`](src/lib/terminalGeometry.ts) closes it — `mayDrivePtyGeometry(isMobile)` is false on a phone *even while it holds the baton*, because taking control means "let me type", never "resize everything to my screen". The gate lives in **module scope** (`deviceMayDrivePty` in `useTerminal.ts`), not a parameter, because "is this a phone" describes the device rather than the terminal and there are a dozen `sendResize` call sites — a threaded parameter has to be right at every one, and missing a single site costs a permanently hard-wrapped PTY on every device with nothing logged. For the same reason the width rule is installed by wrapping the **FitAddon instance at its one construction site** (`installWidthModeFit`) rather than editing the twelve `fit()` calls: CLAUDE.md already records four sites that stayed unguarded across three debugging passes, so a convention cannot be relied on here. Rendering is then a local-only choice — `'pan'` pins the canvas to the PTY's real width (reported by the new `terminal_geometry` message, sent on subscribe and re-broadcast after any resize) and scrolls horizontally, keeping box drawing, tables and diffs aligned; `'wrap'` fits the container and soft-wraps, which reads better for prose. **Desktop behavior is unchanged**: `defaultWidthMode(false)` is `'wrap'`, and `resolveRenderCols` ignores `ptyCols` entirely in that mode. One deliberate consequence — a *desktop browser* dragged narrower than 480px also stops driving the PTY, which is the same rule applied consistently, not an oversight. The pan container must declare **both** overflow axes (`overflow-x: auto; overflow-y: hidden`): per CSS a `visible` axis computes to `auto` when the other is `auto`, so leaving `overflow-y` unset creates a second vertical scroller outside xterm's own viewport. Covered by `src/lib/terminalGeometry.test.ts`; the CSS mechanics were confirmed against a real xterm at 390px (fitted 54 → rendered 120, `scrollWidth` 799 vs `clientWidth` 378) rather than reasoned about.
- **A session is invisible to every device but this machine until it is explicitly shared — and the session LIST is only one of six ways it leaks.** [`sessionVisibility.ts`](server/sessionVisibility.ts) holds the rule (`canSeeSession(isLocalClient, session)`); localhost always sees everything, so the desktop app is untouched. The flag is stored as **`remoteVisible` ("may be seen"), never `hidden`** — that inversion is load-bearing: a `hidden` flag would read as `false` on every row written before the feature existed, exposing the entire backlog the moment it shipped. The absent state must be the safe state. **Gating the list alone produces a feature that only looks like it works**, because five other paths carry the same data: the WS **snapshot** on connect (the largest single leak), **`SESSION_UPDATE` broadcast** (without it the next status change re-introduces the card), **`GET /api/sessions`**, the **17 `/sessions/:id/*` routes** (which include `kill`/`fork`/`resume` — a remote device destroying a session it cannot see), and the two that are genuinely non-obvious: **`TERMINAL_SUBSCRIBE` is keyed by `terminalId`, not session id**, so a remote client could stream a hidden session's live PTY output in full while its card stays invisible; and **`/db/*` is a SECOND store** — `/db/search` and `/db/prompts` return prompt *text*, so hiding a live session does nothing for its history. The REST gate is **one `router.use('/sessions/:id', …)` middleware, not 17 per-route checks**, for the same reason `deviceMayDrivePty` lives in module scope: a per-site check is only as good as the newest site. Three rules hold it up. **(1) A hidden session 404s, never 403s** — a remote client must not be able to tell "no such session" from "hidden from you", or the status code enumerates session ids. **(2) An unresolvable subject fails CLOSED** — a terminal with no owning session (an ops shell, or a PTY whose first hook hasn't landed) is denied to remote clients, and an *archived* session, having no in-memory record to carry the flag, resolves to hidden deliberately: a session that has ended can no longer be opted in through the UI, so treating "no live record" as permissive would build a growing set of permanently readable history that no control can revoke. **(3) `PUT /sessions/:id/remote-visible` is localhost-only** — anything that can reach the port must not be able to grant itself access. Use [`isLoopbackAddress`](server/presenceManager.ts) everywhere, never a second hand-rolled compare, so the auth gate, the 🖥/📱 split and this agree on what "this machine" means. Covered by `test/sessionVisibility.test.ts`.
- **The terminal's DOM renderer draws the selection highlight from a different pixel formula than the glyphs it's supposed to cover — on any line mixing CJK and Latin text, they visibly diverge.** xterm's default DOM renderer forces each CJK glyph's `<span>` to exactly 2 cell-widths via compensating CSS `letter-spacing` (the fallback CJK font's real glyph width never matches the assumed monospace cell width). The selection-highlight overlay is a separate element positioned from idealized `column * cellWidth` math that never learns about that compensation. Measured directly via `getBoundingClientRect()` in a harness (not eyeballed): a uniform 13px drift across the whole selected box on a reproduction line — same width, rigidly shifted, not per-character smearing. **The selected text itself was never wrong** — `term.getSelection()` reads the buffer, independent of how it's painted — this is a pure paint-layer bug, matching what a user will describe as "the highlight looks like a display glitch, the copied text is probably fine." Fixed by loading `@xterm/addon-canvas` (`useTerminal.ts`), which paints both glyphs and selection from the same direct pixel math — confirmed via the same harness at 0px measurable drift. Verified NOT to interact with two other subsystems before shipping: `.xterm`/`.xterm-viewport`/`.xterm-screen` (which the pan-mode CSS above targets) all still exist under canvas mode — the addon only replaces how row *content* paints — and `extractXtermSelection()` reads `term.getSelection()` rather than scraping DOM text, so the AI-popup select-to-translate flow is unaffected. **A second, unrelated bug shares the same surface**: xterm's default double-click word-boundary set doesn't include fullwidth CJK punctuation, so double-clicking a Latin word next to one over-selects across it (confirmed: double-clicking "Claudekit" in "加上 Claudekit、Anthropic" selected `"Claudekit、Anthropic"`) — renderer-independent (reproduces identically before and after the CanvasAddon fix), so it needed its own fix: `wordSeparator` extended with `CJK_WORD_SEPARATORS`, additive to xterm's own default (`DEFAULT_WORD_SEPARATOR`, confirmed byte-for-byte against a real `Terminal` instance rather than hand-transcribed) so existing ASCII word-selection is untouched. **Curly quotes in source are a real hazard, not a style nit**: an early version of `CJK_WORD_SEPARATORS` had its curly quotes (U+2018/2019/201C/201D) silently normalized to straight ASCII quotes while being typed into a single string literal, which closed the string early and broke the build — caught only by re-running `tsc`, not by reading the diff. Splitting the literal in two and diffing actual codepoints (`[...str].map(c => c.codePointAt(0))`) is what actually confirmed the fix; do the same after ever touching this line. Covered by no automated test — there is no unit-test surface for sub-pixel rendering — verification is the harness screenshot methodology itself: build a real xterm instance with the app's exact font/options, write the reproducing text, click or select programmatically, and measure `getBoundingClientRect()` deltas rather than trust a screenshot glance.
- **A component rendered without `key={sessionId}` keeps its local state across a session switch — and `QueueTab` proved it twice, not once.** Neither `<QueueTab>` render call site in `DetailPanel.tsx` keys the component by session id, so switching the visible session updates the `sessionId` prop on the SAME instance rather than unmounting it. The real coverage is `QueueTab.test.tsx`, which renders the actual component and calls RTL's `rerender()` — not two separate `render()` calls, and not a `key`-forced remount — specifically because `rerender()` is the one way to reproduce "same instance, new `sessionId` prop," which is exactly what `DetailPanel` does today. Proven meaningful by reverting to the original `useState` block: all 3 component tests fail, including the dual-mount one showing an empty box where "typed in the strip" should have appeared — the independent-instances bug, caught exactly as predicted.
- **The prompt queue is SERVER-backed — a queue that lives only in IndexedDB is a different queue on every device.** Until Aug 2026 `promptQueue`/`queueAutomation` existed solely in each browser's Dexie store, so the desktop app and a phone at `http://<lan-ip>:<port>` kept entirely private queues for the same session that never synced — the reported symptom was `QUEUE (0)` on the phone for a session with a full queue on the Mac. There was no server-side queue table at all, so nothing *could* sync; the workspace snapshot carries queue items but is explicit save/restore (and its auto-save is single-writer), never live sync. The `session_queues` table is now the shared source of truth, mirrored to by every device and fanned out over `QUEUE_UPDATE`. **Items and automation are stored as opaque JSON, not normalized columns** — the server runs no logic on queue items (the scheduler is entirely client-side), so normalizing would put a second copy of the ~18-field `QueueItem` type on the server that must track the client's forever, where forgetting a field silently drops user data; a JSON blob carries new fields for free. Four rules hold it up. **(1) The echo guard is mandatory** — the server broadcasts every write back to the sender, so applying your own echo marks the store dirty, pushes again, and ping-pongs forever; `originClientId` (from `getClientId()`) plus the `_skipServerPush` set closes both halves, and it is deliberately SEPARATE from the existing `_skipPersist` (that one suppresses the IndexedDB write after a local DB load; conflating them either re-echoes remote changes or stops local edits syncing at all). **(2) Seeding is keyed on "the server has no RECORD", never "the server has no items"** — an empty queue must be a real stored record, or clearing a queue on one device lets the other re-seed from its stale local copy and resurrect the deleted prompts; that distinction is why `decodeQueueRow` returns a record for `[]` and null only for a missing row. **(3) The endpoints live under `/sessions/:id/queue` on purpose**, inheriting `requireVisibleSession` so a remote device cannot read the queue of a session that has not been shared with it — but `GET /api/queues` (the bulk boot-hydration route) sits OUTSIDE that path and therefore filters for itself; a bulk endpoint added later is exactly where the six-path audit in `sessionVisibility.ts` stops covering you. **(4) Dexie is kept as an unchanged local cache** — a failed sync degrades to today's behavior instead of losing work. Covered by `test/sessionQueueCodec.test.ts` (pure, always runs) and `test/sessionQueueDb.test.ts` (live SQLite). **`server/db.ts` opens better-sqlite3 at module scope against Electron's ABI, so it cannot load under system Node and every other server test stubs `db.js` out entirely** — which is why the encode/decode logic was extracted to the import-free `sessionQueueCodec.ts` rather than left inside db.ts where nothing could reach it. The live-SQLite suite skips on an ABI mismatch (`npm rebuild better-sqlite3` to run it, `npm run electron:rebuild` to restore), and its catch **re-throws anything that is not an ABI error**: a bare `catch { db = null }` turns any import failure into a skip, which is how an earlier revision of that file silently "passed" by skipping 8/8 forever after a typo in the import path.
- **The queue's "no-work fallback" cannot tell a silent CLI from a human who just hasn't pressed Enter yet — with `autoEnter` off, the two are the SAME observation.** `onceGateDecision`/`chainGateDecision` ([`queueScheduler.ts`](src/lib/queueScheduler.ts)) serialize queued prompts using two acceptance signals (a busy-status poll, and `session.lastActivityAt` advancing past when the gate opened) plus a last-resort timer (`NO_WORK_FALLBACK_MS = 300_000`, 5 min) that releases the gate for a prompt the CLI never acknowledges at all. Both signals require the CLI to actually *receive* the prompt — but `autoEnter` off means `sendToTerminal` deliberately types the prompt and never presses Enter, so with it off **neither signal can ever fire until the human submits**. The 5-minute timer doesn't know the difference between "the CLI silently no-op'd" (what it exists to catch) and "the user is still reading the terminal" (completely normal) — so after ~5 minutes of a perfectly ordinary review pause, the gate released the NEXT queued item, which typed itself in on top of the still-unsent previous one with no separator. The pure gate functions themselves never changed — the bug was entirely in which constant the call site chose, so covering it needed the REAL shipped constants, not a local test fallback (same lesson `NO_WORK_FALLBACK_MS`'s own history already taught once, for a different trigger — `/compact`'s hook-less busy phase). Covered by `queueScheduler.test.ts`'s `resolveNoWorkFallbackMs` block — reverting to always returning `NO_WORK_FALLBACK_MS` turns exactly 3 tests red.

- **A press-and-hold drag gesture must branch on `pointerType`, and a gesture test that holds perfectly still is testing nothing a hand does.** `useRoomDragReorder` shipped with one path: dwell `HOLD_MS` (350 ms), and cancel on any travel past `MOVE_CANCEL_PX` (8 px). - **A terminal has MANY subscribers, not one.** `Terminal.wsClient` was a single reference, so a second device subscribing silently stole the output stream and the first device's terminal froze with **no error raised anywhere** — the other half of "sessions look messy after connecting from my phone". One more trap: a bare `.noteBody code { background }` rule (0-1-1) outranks highlight.js's `.hljs` (0-1-0) and repaints every fenced block into unreadable light-on-light — scope inline-code styling as `:not(pre) > code`.
- **Never add a static import of a heavy component to `main.tsx` / `App.tsx` / `AppLayout`** — those are the eager roots; use `lazy()`. Eager JS is 1,268,373 bytes (was 2,523,500). No linter catches a regression: after touching an eager root, run `npm run build` and confirm the entry chunk has **zero** static chunk imports (recipe in [views-routing.md](docs/feature/frontend/views-routing.md)). Do **not** "fix" bundle size with `manualChunks` — Rollup groups a package's shared deps into the same chunk, which is how `@react-three/fiber`'s zustand once dragged all of Three.js into the entry.
- **`db.insertFullPrompt()` must run before `pushPrompt()` and share its timestamp** — `promptHistory` is capped/truncated in memory and `upsertSession` re-inserts from that capped copy; the full row written first wins via `INSERT OR IGNORE` on `UNIQUE(session_id, timestamp)`. Reorder them and SQLite silently keeps truncated prompt text.
- **A session's ops shell must be flagged and torn down** — the optional "Commands Terminal" spawns a *second* PTY per session. It must carry `isOps: true` (so `terminalCapacity.ts` keeps it out of the 50-**session** budget; the absolute PTY ceiling is `MAX_TERMINALS = 130`), and every teardown path (`killSession`, `DELETE /api/sessions/:id`, `clearAllSessions`) must close `session.opsTerminalId`. It is a bare login shell that never exits on its own. Miss either half and the cap fires early with a number the user can't reconcile with the session count they see — which is exactly how a single 50-PTY cap came to reject new sessions at ~25.
- **`ArchivedSession` carries only what the UI reads** (`sessionId`, `startedAt`, `endedAt`, `promptHistory`) — it is built solely by `toArchivedSession()`. Adding a field without adding a consumer reintroduces the ~46 KB/entry of write-only logs it was slimmed to remove.
- **Never write test/debug screenshots to the repo root** — Playwright/MCP captures and scratch images go to `test-screenshots/` (gitignored) or `/tmp`; images that ship live in `static/` only. `.gitignore` blocks committing any stray image outside `static/`, but root dumps still clutter the working tree, so always pass an absolute path under a scratch dir when capturing.
- **`npm run typecheck` only ever checked `src/` — `server/` had never been type-checked by any script, silently, for an unknown span of this project's history.** The root `tsconfig.json` scopes `"include": ["src"]`; `server/`'s own `tsconfig.server.json` (`"include": ["server", "src/types"]`) exists but nothing invoked it — not `typecheck`, not `lint` (also `src/`-only), not the one CI workflow (`build-windows.yml`, which only runs `electron:build:win` and never typechecks at all). Found by an align-docs audit agent investigating a `hook-system.md` finding; running it directly surfaced 18 real errors that had been accumulating invisibly: a dead `KNOWN_EVENTS` entry referencing 5 nonexistent `EVENT_TYPES` properties (Gemini-CLI leftovers, silently `undefined` at runtime), two redundant-but-harmless `{ok: x.ok, ...x}` spreads, a real `dueDate: string|null|undefined` vs `AgendaTask.dueDate?: string` mismatch in the agenda PUT handler, `FileHandle` imported from the wrong module (`fs` instead of `fs/promises`), and a control-flow narrowing gap in `deleteSessionFromMemory` where TypeScript couldn't see that `!session` already implied `resolvedId` was non-null across a ternary. All 18 fixed; `npm run typecheck:server` / `typecheck:all` now exist as separate scripts (not merged into `typecheck` itself, matching `lint`'s existing `src/`-only scoping) so this can't silently reopen unnoticed — but nothing *runs* `typecheck:server` automatically yet, so a regression here still won't surface on its own.
