# Session Detail Panel

## Function
Slide-in panel showing comprehensive session information across 7 tabs, with a session switcher strip, session control bar, and two mutually-exclusive layout modes (side-by-side split, stacked).

## Purpose
Primary interface for interacting with a single session. Aggregates terminal, project browser, ops commands, conversation transcript, AI-popup history, notes, and prompt queue in one view, plus per-session controls (resume/kill/mute/alert/room) and a horizontal switcher to jump between active sessions.

## Implementation

### Panel shell
- `DetailPanel` wraps everything in `ResizablePanel fullscreen`. The outer overlay is `display:none` (not unmounted) when no session is selected, so `ProjectTabContainer`/terminal state survives deselection.
- `lastSessionRef` keeps the most-recent session as `displaySession` so child containers stay mounted after deselect.
- Minimizable to a draggable badge (`DraggableMiniBadge`), position saved to `localStorage['mini-badge-pos']` (`MINI_BADGE_POS_KEY`). Click restores (only if it wasn't a drag). Its label comes from `sessionDisplayTitle(session)` (`src/lib/sessionDisplayTitle.ts` — `title || projectName || 'Unnamed'`), so an untitled session shows its project instead of a meaningless "Unnamed". The badge is `position: fixed` and sizes to its content, so the label is capped at `maxWidth: 220` with ellipsis — an unbounded title would push it past the viewport edge; the full text stays in the `title` tooltip.
- **Maximize / Restore**: SessionSwitcher renders a maximize/restore toggle (`MaximizeIcon`/`RestoreSizeIcon`) backed by uiStore `maximized` (default `false`, **not** persisted; `setMaximized`/`toggleMaximized`). When on, the panel's own session tab strip is hidden — forcing nav back to the slim top bar — to give the terminal more space. (The global Header + NavBar are already hidden whenever the panel is in view — see "Dashboard top-bars auto-hide" below.) `DetailPanel` reads `maximized` and exits maximized mode when the panel closes (no session selected) so reopening always starts un-maximized.
- **Left-docked nav rail**: uiStore `navPosition` (`'top' | 'left'`, persisted to `localStorage['nav-position']`; `setNavPosition`/`toggleNavPosition`) controls where the session nav lives. SessionSwitcher renders a dock-left/dock-top toggle (`DockLeftIcon`/`DockTopIcon`). When `navPosition === 'left' && !maximized`, DetailPanel applies the `panelInnerLeft` class (horizontal `rail | content` layout) and SessionSwitcher renders a vertical rail instead of the top strip; maximize always overrides back to the slim top bar. The rail is `230px` wide (`.switcherBarVertical`). In the narrow rail the control block lays out as clean stacked rows: KILL/MUTE/ALERT on one line, the room `<Select>` (tagged `.roomSelect`, made `flex: 1 1 100%`) dropping to its own full-width line, and the toggle icons spread `space-between` on theirs — instead of all of them wrap-cramming onto shared lines.
- **Fold / expand the left rail**: uiStore `navRailCollapsed` (boolean, persisted to `localStorage['nav-rail-collapsed']`; `setNavRailCollapsed`/`toggleNavRailCollapsed`) folds the left rail to a thin `38px` strip. The toggle only applies to the left dock — `isRailCollapsed = navPosition === 'left' && !maximized && navRailCollapsed`. When **expanded**, a fold button (`CollapseRailIcon`, ◀◀) appears in the rail's control cluster (after maximize, before minimize) — rendered only while vertical, since top-dock has no rail to fold. When **collapsed**, SessionSwitcher early-returns a minimal strip (`.switcherBarVertical.switcherBarCollapsed`, a compound selector that overrides the `230px` width) holding just an expand button (`ExpandRailIcon`, ▶▶) and an active-session count pill (`.railCollapsedCount`, properly pluralized); the right-border divider is preserved and `.mainCol` reclaims the freed width. Collapse is **instant** (no width transition) to avoid xterm `fit` resize thrashing, mirroring how maximize toggles layout. Maximize still overrides to the slim top bar regardless of `navRailCollapsed`.
- **Header title row sizing** (`.switcherToggle` / `.switcherNameDisplay`, shared by top bar + rail): the title (`.switcherNameText`) is the row's focal point — `13px`/`600`/`--text-primary` — beside a `9px` status dot, an `18px` index chip, and the pin/edit/tag/note hint icons (`13px`, `.switcherEditHint`, `opacity: .55` until `.switcherName:hover`). The top bar is `38px` tall / `12px` base font — `48px` when a progress remark wraps onto its own line below. In the narrow rail, `.switcherNameDisplay` is allowed to **wrap** so the `LabelChip` + project name drop to a line below the title instead of crushing it onto a 3–4-character ellipsis.
- Header / title / rename live in **SessionSwitcher**, not DetailPanel — the top row shows a status dot, session-index chip, the title with inline double-click rename (`setSessionTitle`, no separate EditableTitle component) plus its pin/rename/label/note hint icons, the optional progress-remark row beneath, optional project name, status badge, model, duration, the `SessionControlBar` (passed via the `controls` prop), the room filter, the sort-by-recent-activity toggle, then the trailing control cluster in order: status-colour legend, compact/detailed toggle, dock-left/dock-top toggle, maximize/restore toggle, the fold-rail toggle (left-dock only), and the minimize button. In the 230px left rail these eight 26px icons exceed the row's 213px, so `.switcherBarVertical .switcherMeta` sets `column-gap: 4px` to keep all seven toggles on one line; the minimize button wraps below them (as it already did with six toggles). Adding a ninth icon requires re-checking that arithmetic.
- **The model badge (`.detailModel`) is clamped to one ellipsised line, capped at an absolute `max-width: 220px`, with the full value on `title` hover.** `model` is data the panel doesn't fully control (hook payloads, restored snapshots, and legacy rows that stored a whole launch command — see [Session management](../server/session-management.md)); unclamped, a long value wrapped to three full-width lines and pushed the meta row past the rail's right border, the overflow already documented on `.switcherBarVertical .switcherToggle`. The cap **must not be a percentage**: `.switcherMeta` is deliberately `flex-shrink: 0` (status/duration/controls must never squash), so in the top bar it sizes to max-content, and a `%` max-width resolving against that content-sized box is circular — treated as indefinite during intrinsic sizing, it let the row grow to the untruncated 972px (a 1101px meta spilling 581px past a 520px window) while only the inner span looked clamped. A definite 220px enters intrinsic sizing directly; in the rail the item's own flex-shrink plus `min-width: 0` pull it back to the 214px the wrapping meta row offers. Verified by measurement in both layouts (top bar at 520px and the 230px rail: zero scroll overflow, zero child overhang).

### Tabs and mounting
- 7 tabs (`BASE_TABS`): PROJECT, TERMINAL, COMMANDS, CONVERSATION (id `conversation`), AI POPUPS (id `aiPopups`), NOTES, QUEUE.
- TERMINAL, COMMANDS, and PROJECT are **always mounted** (hidden via `display:none`) to preserve the xterm instance/scroll and the file-tree/open-file state. CONVERSATION, AI POPUPS, NOTES, QUEUE mount on demand. Each on-demand tab gets a unique React key (`scroll-<id>`) so scroll position doesn't bleed across tabs.
- **Count badges (NOTES / QUEUE)**: each of those two tabs carries a `.tabCount` pill with the session's note / queued-prompt count — the same accent chip the session strip's queue-hint badge uses, so a count reads the same wherever it appears. **Hidden entirely at 0** (no "0" chip) and capped at `99+` so a runaway count can't stretch an already-scrolling tab bar. The digit alone is mute, so the span carries `title`/`aria-label` from `countTitle()` ("3 notes", "1 queued prompt"). Both counts come from **client stores** — `useQueueStore(s => s.queues.get(id)?.length)` (never `session.queueCount`, which isn't synced — the `update_queue_count` WS message is unused) and `useNotesStore(s => s.notes.get(id)?.length)`. Because NOTES mounts on demand, DetailTabs warms the notes cache itself in a `sessionId`-keyed effect; otherwise the badge would read 0 until the tab had been opened once.
- The COMMANDS tab is the session's blank "ops" shell (`OpsTerminalContent`); it only renders when `opsTerminalId || hadOpsTerminal`. With no ops terminal it shows a "CONNECT TERMINAL" placeholder that POSTs `/api/sessions/:id/reconnect-ops-terminal`.
- The TERMINAL tab (`TerminalContent`) stacks `TerminalContainer` over an inline `QueueTab` (`bottomRow`), and exposes Reconnect / Fork / Clone actions:
  - Reconnect (`onReconnect`) shown for ended SSH sessions or sessions with a `startupCommand`; POSTs `/api/sessions/:id/reconnect-terminal`.
  - Fork (`onFork`, Claude/Codex only via `detectCli`) POSTs `/api/sessions/:id/fork`; the new `terminalId` is selected and added to the same room.
  - Clone (`onClone`) POSTs `/api/sessions/:id/clone`; same select-and-room behaviour.
  - `TerminalContainer` is passed `originSessionId={sessionId}` so the select-to-translate popup and "Translate previous answer" toolbar action can fork a floating session (see [Floating Terminal Fork](./floating-terminal-fork.md)).
- **The QUEUE tab's `queueContent` mounts the SAME `QueueTab` a second time**, with a `fullHeight` prop the TERMINAL tab's inline mount does not pass — see [Prompt Queue](./prompt-queue.md#sizing--always-on-strip-vs-full-height-queue-tab). Without it, the tab inherited the inline mount's `.queueBody` (fixed `max-height: 250px`, sized so the always-on strip doesn't crowd out the terminal above it) and showed only 2-3 of a longer queue with the rest of the tab's height going unused. `fullHeight` lets the panel grow to fill this tab's `.tabScroll` instead.

### NOTES tab
Full CRUD over Markdown notes that can embed images and video.

- **One editor, two mount points.** `NoteEditor` backs both the compose box and the in-place edit of an existing note: WRITE/PREVIEW toggle, paste/drop upload, `⌘⏎` save, `Esc` cancel (edit mode only — it `stopPropagation`s so the panel's own Escape handler doesn't close search / exit maximized instead). Do **not** reimplement a "lighter" inline editor for the edit case; the prompt queue's [one-editor invariant](./prompt-queue.md) records what that costs.
- **Rendering** goes through the lazily-imported `NoteMarkdown`: GFM (tables, task lists, strikethrough), highlight.js code blocks, blockquotes, and embedded media. Bare file paths in prose stay clickable — `NoteMarkdown` re-applies `LinkifiedText` to the string children of `p`/`li`/`td`, which plain Markdown rendering would otherwise have silently dropped.
- **Editing is in place and non-reordering**: `updateNote` replaces the note in the list rather than re-sorting, since order is keyed on `createdAt`. `· edited HH:MM:SS` appears only when `updatedAt > createdAt`. The open editor is **derived** (`notes.some(n => n.id === editingId)`), not reset in an effect, so it also closes itself if the note disappears (deleted here or by another client).
- **PREVIEW is disabled while the box is empty** — a preview tab that renders nothing is a fake control.
- Notes are **server-side** (SQLite `notes` table, shared across every client viewing the session) — not Dexie. `src/lib/db.ts` declares a `notes` table that nothing reads or writes; it is dead and must not be mistaken for the store of record.
- The list lives in [`notesStore`](../../../src/stores/notesStore.ts), not in `NotesTab`'s component state, because the tab mounts on demand while its count badge has to be right beforehand. The store is a **cache, never the source of truth**: every mutation goes through the API and only lands in the Map once the server accepted it (`addNote` prepends the echoed row; a non-`ok` response leaves the cache untouched and returns `false`, which is what raises the toast).
- **The API's shapes are load-bearing and easy to get wrong** — all three of these were live bugs:
  - `GET /api/db/sessions/:id/notes` returns a **bare array of snake_case SQLite rows** (`res.json(db.getNotes(id))`), not `{ notes: [...] }`. Reading `data.notes` yields `undefined`, so the tab listed nothing while notes saved fine — a silent, permanent "No notes yet".
  - Rows are snake_case (`session_id`, `created_at`); the UI type is camelCase. `fromRow()` is the one conversion point — skip it and `formatTime(undefined)` renders `Invalid Date`.
  - Delete is `DELETE /api/db/notes/:id` — **by row id, not nested under the session**. A session-nested URL 404s, and since the old call checked neither `resp.ok` nor showed an error, the row silently survived the "successful" delete.
- Fetches go through `authFetch`, so notes keep working when a dashboard password is set (bare `fetch` 401s).
- The store keeps the list **newest-first on write**; `NotesTab` must not re-sort at render time (the old `notes.sort(...)` mutated the array it was handed).

#### Note media (images / video)
- **Bytes never go in SQLite.** `POST /api/db/sessions/:id/note-media` writes the file under `<data dir>/note-media/<id>.<ext>` and records metadata in `note_media`; the note's text stores only `![name](/api/note-media/<id>)`. A 40 MB screen recording therefore costs a ~40-byte row instead of 55 MB of base64 that every notes fetch would reload. Served back by `GET /api/note-media/:id` via `res.sendFile`, whose Range support is what makes `<video>` seekable.
- **Do not model this on `/api/queue-images`.** That endpoint writes to `/tmp` and deletes anything older than 24 h — correct for handing a path to a CLI, fatal for a note read next month.
- **Upload happens on paste/drop, before the note is saved**, so the editor can insert a real URL at the caret. The cost is orphans: media the user never saved, or that an *edit* removed from the text. `sweepOrphanNoteMedia()` (hourly, from `server/index.ts`) deletes rows older than `ORPHAN_TTL_MS = 1h` that no note's text references. The reference check is deliberately **global, not session-scoped** — note text gets copy-pasted between sessions, and deleting media still displayed somewhere is worse than keeping a few stale bytes. Deleting a session calls `deleteNoteMediaForSession` **before** the cascade, because once the notes are gone the sweep can no longer tell that media from a live upload.
- **Filename safety**: files are named from a server-generated 128-bit hex id plus an allowlisted extension, in a flat directory — no caller-supplied text ever reaches `join()`, and `resolveNoteMedia` re-checks the id against `/^[a-f0-9]{32}$/` before serving.
- **SVG is excluded from the MIME allowlist on purpose** — it can carry script and these files are served same-origin, so an inline SVG would be a stored-XSS vector. Allowed: PNG/JPEG/GIF/WebP/AVIF and MP4/WebM/MOV/OGV, each capped at `MAX_MEDIA_BYTES = 25 MB`. Responses carry `X-Content-Type-Options: nosniff`.
- `<video>` renders with `preload="metadata"` — a notes list holding several recordings would otherwise fetch every one of them on render.

### Layout modes (split / stacked) — mutually exclusive
The PROJECT tab shows two layout toggle icons plus a pop-out-to-window icon (wide panels only, `SPLIT_MIN_WIDTH = 700`). Enabling one layout mode disables the other via the shared `turnOff` helper:
- **Split**: `DraggableSplitView` shows Terminal (left) + Project (right) with a `col-resize` divider, ratio clamp 0.15–0.85. Mode flag `split-terminal-project:{sessionId}` (`SPLIT_KEY`), ratio `split-ratio:{sessionId}` (`SPLIT_RATIO_KEY`, also mirrored to a global fallback).
- **Stacked**: `StackedSplitView` shows Terminal (top) + Project (bottom) with a `row-resize` divider, ratio clamp 0.2–0.8 — fits the ~480px panel better than side-by-side. Mode flag `split-stacked-terminal-project:{sessionId}` (`STACKED_KEY`), ratio `split-stacked-ratio:{sessionId}` (`STACKED_RATIO_KEY`, also mirrored to a global fallback).
- The third icon is **not** a layout mode — it is the stateless pop-out action that opens PROJECT in its own OS window; see [Pop-out to a native window](#pop-out-to-a-native-window).
- `effectiveTab` resolves to `'split'`/`'stacked'` when the corresponding mode is on and the active tab is terminal/project; in those modes the always-mounted terminal/project hosts are suppressed (the combined view renders its own single copies to avoid duplicate xterm subscriptions). Both flags restore per-session on session switch (default off so the previous session's state doesn't leak).

#### Pop-out to a native window
The **TERMINAL** and **COMMANDS** tabs can each be popped out into their own lightweight window (draggable to another monitor — Electron gets a real native OS window, a browser tab gets a real detached `window.open` popup) via a `⧉` toolbar button. An in-app DOM panel is confined to the app window, so cross-monitor movement requires a real window. Both popouts open a **content-only** window (just that tab's content, not the whole dashboard) loaded from `/?popout=…` — `main.tsx` detects the `popout` query param before bootstrapping `<App>` and renders the popout view directly:

| Tab | Trigger | Window | View |
|-----|---------|--------|------|
| TERMINAL | `⧉` on `TerminalToolbar` (when `onPopOut` provided) | `electronAPI.openTerminalWindow({ terminalId, originSessionId, label })` → `/?popout=terminal&terminalId=…` | `PopoutTerminalView` |
| COMMANDS | `⧉` on `TerminalToolbar` | same, with the **ops** `terminalId`, `label: 'Commands'` | `PopoutTerminalView` |
| PROJECT | **detach** icon on the PROJECT tab (wide panels) | `electronAPI.openProjectWindow({ path, label: 'Project' })` → `/?popout=project&path=…` | `PopoutProjectView` (wraps `ProjectBrowserView`) |
| SESSION (all tabs) | `DetachIcon` on the session title (`SessionSwitcher`, after rename/label/remark) | `electronAPI.openSessionWindow({ sessionId, label: title })` → `/?popout=session&sessionId=…` | `PopoutSessionView` (wraps `DetailPanel`) |

**Terminal / Commands popout** (`TerminalContent` / `OpsTerminalContent` in `DetailPanel.tsx`): `handlePopOut()` branches three ways — the same `electronAPI.openTerminalWindow` present / present-but-missing (stale preload) / absent chain as `FloatingTerminalPanel`'s own `handlePopOut` (see [Floating Terminal Fork → Pop-out to a native window](./floating-terminal-fork.md#pop-out-to-a-native-window)); the browser-fallback branch is the shared [`openTerminalPopupFallback`](../../../src/lib/popoutTerminalWindow.ts) helper, so all three call sites open the identical `?popout=terminal` window rather than three independently-drifting copies. On the Electron-success branch only, it marks the `terminalId` in `floatingSessionsStore.poppedOut` and calls `electronAPI.unsubscribePty(terminalId)` to release the in-app PTY subscription; the tab then renders `PoppedOutTerminalPlaceholder` ("…open in a separate window — close it to dock here", FOCUS WINDOW button) instead of the live `TerminalContainer`, so only the popout window subscribes to the PTY (no two-subscriber contention; mirrors the fork-popout trick), and **re-docks** the same way: closing the window fires `popout:closed` → `FloatingTerminalRoot` calls `setPoppedOut(id, false)` → the in-app `TerminalContainer` re-mounts and replays the PTY buffer. The browser-popup branch has no such close signal, so it never marks `poppedOut` — the in-app terminal and the popup simply coexist as two live subscribers (safe: `wsClients` is a `Set<WebSocket>`, see [WebSocket manager](../server/websocket-manager.md)). The `⧉` button itself is **always rendered** (there is no Electron-only visibility gate — `canPopOutWindow()` was removed, the button now depends only on `onPopOut` being passed) and still never renders on the fullscreen-overlay toolbar, an unrelated, unchanged omission in `TerminalContainer` itself.

**PROJECT popout** (`DetailTabs.tsx`): the PROJECT tab's **detach** icon (shown on wide panels, next to the split/stacked toggles) is a **stateless action** — `openProjectWindow()` calls `electronAPI.openProjectWindow({ path, label: 'Project' })` (native `BrowserWindow` placed on the second monitor via `computePopoutBounds('project')`, bounds persisted under its own `'project'` key — see [Project Browser](./project-browser.md) — **de-duped by path** so a repeat click focuses the existing window), or falls back to `window.open('/project-browser?path=…', 'aasc-project-<path>')` in the browser. It is gated on the session having a `projectPath`.

Three details of that button are load-bearing and easy to undo by accident:

- **The `window.open` fallback must never run under Electron.** If `window.electronAPI` exists but `openProjectWindow` is missing (a stale preload), the handler returns early and does nothing. Falling through would hand the URL to the shell's [`attachWindowOpenPolicy`](../electron/app-lifecycle.md#windowopen-policy-attachwindowopenpolicy) — and before that policy learned to recognise our own origin, that meant **the user's default browser opening on `http://localhost:<port>`**. A stale preload is a build problem; leaving the app is not a graceful degradation of it. Asserted by `DetailTabs.test.tsx` ("never falls back to window.open under Electron with a stale preload").
- **`DetachIcon`, not a picture-in-picture glyph.** The icon is a window with a title-bar rule and an arrow escaping the top-right corner. It was a PiP box (small box nested inside a big box) left over from the retired in-app `FloatingProjectPanel`, which reads as *an overlay that stays inside the app* — the opposite of what the button does. The title-bar rule is also what separates it from `UnstackIcon`'s plain rect at 14px. **Shared, not duplicated:** `src/components/ui/DetachIcon.tsx` (`size` prop, default 14) backs all three pop-out-to-native-window buttons in this app — PROJECT here, SESSION here, and the floating AI-popup panel's own pop-out (`SessionSwitcher.tsx` passes `size={13}` to match its row's other 13px icons; `FloatingTerminalPanel.tsx` passes `size={12}`; see [Floating Terminal Fork](./floating-terminal-fork.md#pop-out-to-a-native-window)). It was two independently-duplicated copies (here and in `SessionSwitcher.tsx`, the latter's own comment explicitly arguing *against* sharing it) before the floating-popup button — previously a raw `⧉` Unicode glyph — became a third consumer.
- **A `.toggleDivider` hairline sits between the two layout toggles and this one.** Split and stack are *modes*; detach is an *action*. Without the rule all three read as a three-way layout switch. It is `pointer-events: none` so it can never swallow a click meant for the tab button it lives inside. Unlike the terminal popout there is **no placeholder / re-dock** — the in-app PROJECT tab stays fully usable (the popout is a fresh `ProjectBrowserView`, not the live in-app DOM), and in-app side-by-side is still available via the **split** / **stacked** modes. The previous in-app draggable `FloatingProjectPanel` overlay (and its pop-out gestures) was retired in favour of this — a DOM overlay can't cross monitors; only a real OS window can.

**Session popout** (`PopoutSessionView.tsx`, new): the session-title `DetachIcon` (`SessionSwitcher.tsx`, gated on `!!electronAPI?.openSessionWindow`) pops the **whole** session — every `DetailTabs` tab, not just one — into its own window. Its tooltip is now `tooltips.floatSessionPopOut` ("Detach session into its own window" / "Open every tab of this session in a separate OS window you can drag to another monitor.") via the shared `Tooltip` component — it used to be a plain native `title`/`aria-label` pair with no rich styling, the only one of the four detach-to-native-window buttons in the app not wired through `Tooltip`. The other three (`floatProject`, `termPopOut`, and the AI-popup's `floatTerminalPopOut`) already matched; this one didn't. Unlike the two popouts above, this reuses `DetailPanel` itself rather than a purpose-built standalone view: `PopoutSessionView` calls `useSettingsInit()` + `useWebSocket(null)` (same as the other two), hydrates the queue stores the same way `main.tsx`'s `bootstrap()` does (the QUEUE tab needs them, and a `session_update` carrying `replacesId` needs `queueStore.migrateSession()` to see an already-hydrated map — same ordering hazard `bootstrap()` guards against), selects the session by id from `?sessionId=` in its own `useSessionStore`, and renders `<DetailPanel />` under a small fixed "back to main" button.

Session popouts are keyed by `sessionId` in their own `sessionPopoutWindows` Map (`electron/main.ts`) — a separate map from both `popoutWindows` (terminal) and `projectPopoutWindows` — and, like the PROJECT popout, never send `popout:closed`: a whole session has no in-app float to re-dock, the popout and the main window's own `DetailPanel` for the same session just coexist as two live views of the same WS-driven state.

The **return path is the one genuinely new mechanism** here — neither existing popout has one. The "back to main" button calls `electronAPI.returnToMain()`, which round-trips through the main process rather than acting locally: it focuses `mainWindowRef`, sends it `popout:return-to-list` (a main-window-only `useEffect` in `AppLayout` calls `useSessionStore.getState().deselectSession()` on receipt — the session-list view, not merely "the window"), and only then closes the calling popout (`BrowserWindow.fromWebContents(event.sender)` — the handler doesn't look the window up by sessionId, it just closes whichever window asked). Closing the popout via the native window-chrome close button (rather than the in-app back button) does **not** trigger this — it just closes, same as the other two popouts; only the explicit button drives the main window back to the list.

**Known limitations:** the project popout opens at the project root (the float's currently-open file isn't forwarded yet); a select-to-translate fork spawned from inside a popped-out terminal renders in the main window (consistent with the existing fork popout); `DetailPanel`'s own minimize-to-badge control still renders inside a session popout and, if clicked, shrinks the view to a draggable badge within that same small window rather than doing something popout-aware — harmless (click it again to restore) but not yet suppressed there. See [IPC transport](../electron/ipc-transport.md) and [App lifecycle](../electron/app-lifecycle.md) for the native-window side, and [Floating Terminal Fork](./floating-terminal-fork.md) for the shared popout infra.

### Search
- A search bar sits between the tabs and content (`searchOpen` toggles `.hidden`). It shows a match counter (`N/total` or `0 results`) and Prev/Next navigation, which step through the `.search-highlight` DOM nodes.
- **`searchQuery` is one shared string.** DetailPanel owns it; the Cmd+F bar and the CONVERSATION tab's own toolbar search box are both bound to it (`onSearchChange={setSearchQuery}`), so the two entry points can never hold different queries. See [conversation-view.md](./conversation-view.md).
- **The match count comes from the conversation view when that tab is mounted.** `convMatchCount` (`useState<number | null>`) is fed by `ConversationView.onMatchCountChange`; `searchMatchCount` prefers it and falls back to counting `promptHistory` only when it is `null`. It is reset to `null` whenever `activeTab !== 'conversation'`, because `DetailTabs` renders only the active tab (`contentMap[effectiveTab]`) so the reporter unmounts and its last value would go stale. Previously the counter *always* came from `promptHistory`, while the highlight covers assistant/tool/event/system rows too — so it under-reported (e.g. `1/2` against 7 lit rows) and, because `navigateMatch` takes `next % searchMatchCount` over the full `.search-highlight` list, ▲▼ silently skipped real matches.
- `navigateMatch` auto-switches to the CONVERSATION tab, then scrolls the active `.search-highlight` into view (adding `.search-highlight-active`).
- Opened via the `detail-panel:find` CustomEvent (from the keyboard-shortcut handler); closed on Escape or session change.

### Tab switching via keyboard
- DetailPanel listens for the `detailTabs:switchTab` CustomEvent (dispatched from `useKeyboardShortcuts.ts`) and drives `externalTab`, which DetailTabs consumes via `externalActiveTab`. `externalTab` is cleared ~50ms after set so subsequent user clicks aren't blocked. The same `externalTab` mechanism switches to PROJECT when a terminal file link is clicked (`pendingFileOpen`).
- Active tab persisted in `localStorage['active-tab']` (`STORAGE_KEY`).

### SessionSwitcher details
- Session tab cards use a **neutral static frame** (`var(--border-subtle)`); status is conveyed only by the coloured corner badge (StatusGlyph / green ✓), the mini status dot, and (compact mode) the title colour. The old per-status conic-gradient spinner + pulse border animations were removed as a continuous CPU/GPU drain — do not reintroduce always-running gradient/box-shadow animations on cards (the same removal applies to HeaderAgentStrip `.miniRobot` chips, which keep their static status-coloured border). The `.sessionTabIndex` badge sits at `left: -9px`.
- **Completed badge**: a session that transitions to `waiting` (or, for Codex, jumps `idle`→`waiting`) while not selected gets a pulsing **green `✓` badge** (`attentionIds`, `.sessionTabAttentionBadge`), cleared when switched to. It signals "finished its work, ready for review" — green ✓ rather than a red `!` alarm, since completing is a good state.
- **Per-status glyph badge** (`StatusGlyph` + `.sessionTabStatusBadge`): the top-right corner shows a **distinct icon per status** so states are tellable apart by shape, not colour alone (`waiting`/`prompting` even share cyan): `waiting`→✓, `approval`→`!`, `input`→`?`, `working`→spinner, `prompting`→up-arrow, `idle`→pause-bars, `connecting`→ellipsis, `ended`→✕. The badge is filled with the status colour (`--robot-color`) and carries a dark glyph for contrast. It is **mutually exclusive** with the green ✓ completed badge — the green ✓ wins while `needsAttention`, otherwise the per-status glyph shows. The mapping is **backend-agnostic**: Claude and Codex derive status from the same hook events (`sessionStore` has no per-backend status branching), so the same real-world state shows the same icon on either CLI.
- **Title clearance**: `.sessionTabTitle` carries `padding: 0 18px` (`0 14px` compact) so the absolutely-positioned index badge (top-left) and completed badge (top-right) never overlap the title text.
- **Queue-hint badge** (`.sessionTabQueueBadge` + `QueueBadgeIcon`): when a session has queued prompts, its tab card shows a cyan **list-glyph + count** (e.g. `≣2`) rendered inline at the **start of the title** (an `inline-flex` span inside the `-webkit-box` line-clamp, so the title still wraps/clamps around it and the badge is never pushed out). Hidden entirely when the queue is empty (no `0`). The count comes from the **client `queueStore`** — `useQueueStore(s => s.queues.get(sessionId)?.length ?? 0)`, matching the QueueTab's `QUEUE (N)` header — **not** `session.queueCount`, which is never synced to the client (the `update_queue_count` WS message is defined but unused). Because the tab strip lists the *non-current* sessions, the badge surfaces "which other agents have work waiting" at a glance; the current session's queue shows in its own QueueTab.
- **External-session badge** (`.sessionTabExternalBadge`): when `session.isExternal` is true, the tab card renders a distinct **`⌁` glyph** inline at the **start of the title** — after the queue badge, before the title text — inside the same `.sessionTabTitle` line (an `inline-flex` span so it flows with and clamps alongside the title). Its `title`/`aria-label` read "External session — running outside the dashboard (limited tracking)" / "External session". Styled with an **amber accent** (`--accent-orange` text on a 16%-tinted background), mirroring `.sessionTabQueueBadge`'s shape but reading as "limited / not fully controlled" rather than alarming red. `isExternal` is a new [Session](../server/session-management.md) field marking a session the dashboard didn't launch (external terminal, or a CLI started before the hooks were live), so its tracking is limited; only sessions carrying the flag show the marker.
- **Per-session pin (header)**: a `PinIcon` hint button — **leads** the title-row cluster (before rename/label/note), since pinning changes the session's lifecycle/list-position rather than annotating it the way the other three do. Toggles the same `session.pinned` / `useSessionStore.getState().togglePin(sessionId)` the other-session tab strip's own pin (`.sessionTabPin`, a 📌 emoji glyph — a deliberately different visual, since an emoji among this row's vector line-icons would look inconsistent) and [RobotListSidebar](../3d/robot-system.md) already drive — one shared boolean, three independent toggle surfaces. Tooltip label flips between `tooltips.sessionPin` and `tooltips.sessionUnpin` via the same `{...(session.pinned ? tooltips.sessionUnpin : tooltips.sessionPin)}` spread `SessionControlBar`'s mute/alert buttons use for their own state-dependent copy. Carries the same `onMouseDown` preventDefault + `onDoubleClick` stopPropagation guard as the note/detach buttons below — without it, a double-click meant for the pin toggle also fires the parent `.switcherName`'s double-click-to-rename.
- **Per-session label**: a tag button next to the title (in the header) opens `LabelPicker` (built-in ONEOFF/HEAVY/IMPORTANT + custom labels with colors); the chosen label renders as a colored `LabelChip` next to the title in the header and as a small read-only chip/dot on the strip cards. Client-only, stored in [`labelStore`](./state-management.md) (no server).
- **Per-session progress remark**: a free-text note ("what is this session waiting on?") the user maintains by hand, rendered on its own row **under the title**. Unlike the label it is **server-persisted** — `sessionStore.setSessionRemark` optimistically updates the in-memory session and `PUT`s to [`/api/sessions/:id/remark`](../server/api-endpoints.md) → `setSessionRemark` → the `sessions.remark` column ([database](../server/database.md)). Capped at **200 chars on both sides** (client `maxLength`, server `remarkSchema`); it renders on one line and ellipsizes, so the cap must stay in sync at both ends.
  - **Entry point is the note icon** (`NoteIcon`), the fourth hint button in the title row after pin (`PinIcon`), rename (`EditIcon`), and label (`TagIcon`). There is deliberately **no empty-state placeholder row**: the row only renders when `currentRemark || remarkEditing`, so the `38px` top bar grows to `48px` only for the sessions that actually carry a remark (an always-on `+ add remark` row taxed every session a second line). The icon gets `.switcherHintActive` — the shared "lit" style also used by the tag button while its picker is open — whenever the session has a remark, so the bar still signals "a note exists" at a glance.
  - **Commit semantics**: Enter and blur (click-away) **save**; Escape **discards**. An empty string is a legitimate edit that *clears* the remark (stored `NULL`), so no truthiness guard may be added on the commit path. Clicking the note icon while the editor is open also saves — the button calls `preventDefault()` on `mousedown` so the input never blurs; without that, blur→commit would flip `remarkEditing` false *before* the click ran and the toggle would immediately re-open the editor it was meant to close.
  - **Rail width trap**: in the left rail `.switcherToggle` is a **wrapping column**, which reverses the meaning of the top-bar `flex: 0 0 100%` on `.switcherRemark` — there it sizes the *main* axis (height), leaving the width to fit the text, so a long remark grew past the rail edge (measured `674px` inside a `230px` rail). `align-self: stretch` does **not** fix it: a wrapping column stretches an item to its flex *line*, whose width is set by its widest item — the overflowing text itself. The `.switcherBarVertical` override therefore pins `flex: 0 0 auto` + `width: 100%`; only a definite width breaks that circle and lets `text-overflow: ellipsis` clip.
- **Room grouping**: sessions sharing a room render inside a room-colored frame (`ROOM_COLOR_PALETTE`, matching HeaderAgentStrip), ordered by `room.listOrder ?? room.roomIndex ?? MAX_SAFE_INTEGER` (see the reorder bullet below); orphan sessions follow. A multi-select **room filter** dropdown (funnel icon) narrows the strip (`selectedRoomIds`); it treats the current session's card like any other (the header above the strip always shows the current session). Room framing is skipped entirely in activity-sort mode (below).
- **The current session is listed too (Sep 2026)**: the strip used to drop the selected session — it began as a "switch to another session" list — which also removed any room frame whose only session was the current one, so the room you were working in vanished from the rail (the reported case: SMS Fixing, SMS OPS's only session, left no SMS OPS frame). `sortedSessions` now keeps it, in both the rail and the top bar, numbered exactly as the header shows it (the index map always counted it). Its card carries `aria-current="true"` and `.sessionTabCardCurrent` — a room-coloured border plus a 10% tint (`--room-color` is inherited from the frame; a loose card falls back to `--accent-cyan`), not a left bar, because the sequence badge sits on the card's left edge. It does not lift on hover (`cursor: default`), since **clicking it is a no-op**: `handleSwitch` returns early for the current id, because `selectSession` records the outgoing id as `previousSessionId`, and re-selecting the current session would make it its own "previous" and silently break the switch-to-previous shortcut (`useKeyboardShortcuts`). Its pin toggle still works. A workspace with only the current session now shows a one-card strip instead of none. Two things listing it newly exposed, both fixed and covered by the same describe block:
  - **The completed ✓ is acknowledged by viewing.** The attention effect deletes the current id from `attentionIds`, and the current card is passed `needsAttention={false}` (covering the frame before the effect runs). Otherwise a session reached via the sidebar, Cmd+N or Cmd+E — not a strip click, which already cleared it — would show its stale ✓ on the current card, and clicking it (a no-op) could not clear it.
  - **Rename only starts from a double-click that BEGAN on the current card**, and **an untouched pre-fill is never saved**. The card now stays put after the click that selects it, so a double-click's second click lands on it: `currentAtPress` records `isCurrent` at the sequence's first press (`e.detail === 1`), and `beginEdit` refuses unless it was already current — a double-click that opens a session is "open", not "rename". The "Double-click to rename" hint shows only on the current card. Both rename boxes (card and header) compare against what they were pre-filled with (`editFrom` / `headerEditFrom`): an untitled session pre-fills its project name, and saving that untouched was a manual rename that permanently suppresses the automatic title (the header had the same flaw before).
  - **Known gap — the header changes height when the project line appears or disappears** (`secondaryName` is conditional): switching to an untitled session moves the list up ~21px, so the second click of a double-click can land on the card below. This predates listing the current session (before, the clicked card itself vanished, so the second click *always* hit another card).
- **Sort by recent activity** (`SortByActivityIcon`, second toolbar slot, right after the funnel): toggles uiStore's `sessionSortMode` between `'room'` (default) and `'activity'`. In `'activity'` mode `tabRenderItems` returns a flat list of `{type:'session'}` items — no room frames, since a room can only sit in one place while its sessions belong all over a recency-ranked list — ordered by [`sortSessionsByActivity`](../../../src/lib/sessionSort.ts) (pinned first, then `lastActivityAt` descending, tie-breaking title then `sessionId` for a total order). Status is ignored: a stale `working` session sits below a fresh `idle` one. The room **filter** still applies; only the frames vanish. Badge numbers are unaffected — `sessionIndexMap` is always derived from the status sort, so rows reorder without renumbering (which is why the strip's numbers look unsorted in this mode, by design). That sort is [`numberedSessions()`](../../../src/lib/sessionSort.ts) (Sep 2026), shared with Cmd/Ctrl+Alt+1-9 and the Cmd/Ctrl+Alt+0 "go to session #" box, so a number typed is the number on the card — see [Keyboard Shortcuts](./keyboard-shortcuts.md).
- **Built-in RECENT frame (Sep 2026)**: in room mode, `tabRenderItems` starts with a `{type:'recent'}` item, rendered as a dashed frame labelled RECENT above every user room. It lists sessions with recent work, and each one is **also** listed in its own room, under the same `#` (numbers come from `sessionIndexMap`, like everywhere else). It is not a `Room`: nothing stores it, `visibleRoomIds` keeps only `type 'room'`, so it takes no part in drag or ▲▼ (▲ on the first real room stays disabled), and its header has only the collapse toggle — no grip, no ▲▼, no kill-all, no rename. **What counts** ([`recentSessions.ts`](../../../src/lib/recentSessions.ts)): a turn running now (`prompting`/`working`/`approval`/`input`), or real work within `RECENT_WINDOW_MS` (30 min) — the last prompt, or the last hook event from an allow-list that leaves out `SessionStart`/`SessionEnd` and the server's own markers (`ServerRestart`, `ResumeRequested`, …). **Never `lastActivityAt`**: the server stamps it on every hook, SessionStart included, and a workspace restore resumes every session, so it would put the whole workspace in RECENT for half an hour after each launch. **Order**: pinned first, then newest *prompt* first, never-prompted last, then title and id. Not by latest event, because two working sessions fire tool events every few seconds and their cards would keep swapping under the cursor. **Clock**: a 60 s tick (`RECENT_TICK_MS`) re-checks, since a session goes quiet without any update arriving; `recentIdsKey` (the ordered ids as one string) is rebuilt from the fresh `sessions` each update and tick, and `tabRenderItems` depends on the string, so a tick that changes nothing re-renders nothing. The frame takes its sessions from `filteredSessions`, so the room filter narrows it too; it is absent in activity sort (already a recency list, with no frames) and when nothing is recent. Collapse is uiStore's `recentRoomCollapsed` (`localStorage['recent-room-collapsed']`), since there is no `room.collapsed` to use. The RECENT copy of the current session keeps the current look but not `aria-current`, which stays on the room copy so the list announces one current item (`isRecentCopy` on `SessionTabCard`). **Colours** (`.recentRoomGroup`): `--room-color: var(--text-secondary)` for the dashed border and triangle, but the label and collapsed count use `--text-primary` — measured from pixels, `--text-secondary` fell below 4.5:1 in solarized (2.92), nord and monokai, and `--text-primary` is the only neutral that clears it in all ten themes (solarized lowest: label 5.00, count 4.66 with the count pill's tint halved to 8%). `.roomCollapseToggle` also gained the `:focus-visible` ring `.roomMoveToggle` already had, for every frame — in RECENT it is the only control.

Fixed with two independent signals, not one: the glyph FAMILIES now differ (filled disclosure triangle vs stroked arrow-with-a-shaft), and the dividers group the row into `[grip collapse] | [▲▼] | [skull]`. Two signals because either alone is one restyle away from collapsing back; `SessionSwitcher.test.tsx` asserts both (fill/stroke + shaft presence, and divider count/placement). The session cards render as siblings **below** the header row and keep their column stacking in the rail; the horizontal top-bar layout is unchanged (the group is already a row there).
- **Room reorder (drag + ▲/▼, Sep 2026)** — writes `Room.listOrder`, a field added specifically so this can exist: `Room.roomIndex` is NOT a display-order hint, it's the room's world-space grid slot in the 3D cyberdrome (`roomGrid.ts`'s `computeRoomCenter`, the camera-focus target in `SceneOverlay`, and the room's color in `HeaderAgentStrip`/here — `roomIndex % PALETTE.length`). Wiring the sidebar's reorder controls to `setRoomIndex` would have silently relocated the room's walls/doors and recolored it as a side effect of reordering a list. `listOrder` is a separate field with zero 3D consumers; the sort falls back `listOrder ?? roomIndex ?? MAX_SAFE_INTEGER` so existing rooms don't visibly reshuffle until reordered for the first time. **▲/▼** (`moveRoom` in `SessionSwitcher.tsx`) swap-reindexes every *visible* room frame (0..N-1) rather than patching two raw values, so `listOrder` never depends on a borrowed `roomIndex`/`MAX_SAFE_INTEGER`; disabled at the first/last visible room. **Drag** (`useRoomDragReorder.ts` + pure `roomDragReorder.ts`) mirrors the queue's own press-and-hold pointer-event gesture (`useQueueDragReorder.ts`) rather than native HTML5 `draggable` — that hook's own header comment records that native drag never fires on touch, which is why the queue replaced it; a fresh room implementation would reintroduce the same gap. Kept as separate files rather than generalizing the queue's, since a room list is always a single vertical column (no grid axis to pick), a genuinely simpler geometry. "Visible" rooms means frames actually rendered this tick (`roomSessions.length > 0` after the active filter) — adjacency is defined by what's on screen, not by position in the full `rooms` array. Covered by `SessionSwitcher.test.tsx`'s "room reorder" block, including a regression test that reordering leaves every room's `roomIndex` byte-identical, and that the pre-existing kill-all skull still opens `RoomKillConfirmModal` with the three new icons sharing its row.
- **The drag gesture has TWO paths, picked by `pointerType` (Sep 2026 fix)** — and for its first weeks it shipped with only the touch one, which made desktop drag-to-reorder a dead control. `useRoomDragReorder` originally required a `HOLD_MS` (350 ms) dwell before lifting and cancelled the pending drag on any travel past `MOVE_CANCEL_PX` (8 px). That pairing is correct for a finger (a swipe must be able to scroll the rail) and impossible for a hand on a trackpad: a real drag is past 8 px within a frame or two of the press, so **every** desktop drag was classified as a rail scroll and cancelled — with no lift, no caret and no cursor change, i.e. indistinguishable from the feature not existing. `requiresHoldToDrag(pointerType)` now picks the path: `mouse`/`pen` lift as soon as travel passes `MOUSE_DRAG_START_PX` (4 px) with no dwell at all, everything else keeps the hold-first rule byte-for-byte. **Unknown/empty `pointerType` deliberately takes the touch path** — the new behaviour is opt-in for explicitly-identified precision pointers, so an unrecognised device can never inherit a gesture that hijacks a scroll. Both paths share one `lift()` so "what lifting means" has a single definition, and the mouse path falls through to position the drop slot and the carried room on the same event that lifted (otherwise both lag the pointer by a frame for the whole drag). The mouse path also `preventDefault()`s the pointerdown, which stops the browser painting a text selection across every session card the drag crosses — safe only because the handle is a non-focusable `aria-hidden` span with no click behaviour.
- **Why the existing tests did not catch it, which is the reusable lesson**: every test in `useRoomDragReorder.test.tsx` pressed with `pointerType: 'touch'` and then advanced fake timers past `HOLD_MS` with *zero intervening `pointermove`*. That is a gesture no hand performs with a pointing device, so the suite was green against a control nobody could operate. A gesture test that holds perfectly still for the hold window is testing the implementation's happy path, not the input. The `— mouse/trackpad` block now interleaves moves with ~16 ms timer advances to model a real drag, and pins the click-that-never-moves case so a plain press-and-release still cannot commit a phantom reorder.
- **Grab-target size**: `.roomDragHandle` renders an 8×12 glyph but reserves a **24×24 hit box** with `margin: -4px -6px`, which cancels the extra width and height exactly — the glyph's centre and every sibling icon's position are byte-identical to the 12×16 version. The bare glyph is roughly a quarter of the 44×44 touch minimum and easy to miss with a trackpad, which made a gesture that was *also* refusing to start look even more like a dead control. The box overlaps the frame's left padding (nothing is there) and overlaps the collapse button by ~2px, which that button wins by painting later in the same stacking context.
- **Drag feedback — the "carry" preview (Sep 2026)**: the lifted room **follows the pointer** and the rooms it has passed **slide aside** to open the slot it will land in, so the opened slot *is* the drop indicator; on release the room **settles** into it. This replaced a dim-in-place frame (`opacity .4`, `scale .98` — read as "disabled", not "picked up") plus an inset cyan caret drawn *inside* the target frame's top edge (read as "drop into this room", replaced that frame's room glow, and still lit a neighbour on a no-op slot). Each mechanic below is load-bearing:
  - **Pointer-follow bypasses React.** The hook writes the clamped offset (`clampRoomDragOffset` keeps the carried room within the rooms' span) straight to the frame's `--room-drag-dy`, via the `getFrameEl` param (`getRoomEl` → `roomElsRef`). The switcher renders every session card, so a state update per pointermove would re-render all of them at pointer rate. React re-renders only when the indicated slot changes: `shifts` = `computeRoomShifts(rects, id, insertIndex)`, applied per frame as `--room-shift`.
  - **Rects are still measured once, at lift.** The slides are transforms and `getBoundingClientRect` includes transforms, so re-measuring mid-drag would feed the slid boxes back into the hit test.
  - **Slide transitions exist only under `.roomDragActive`.** On drop, the class and the shifts vanish in the same render that commits the new order, so the after-change style has no `translate` transition and the slid rooms stay exactly where they are; a live transition would make each jump one pitch and slide back. `computeRoomShifts` previews every passed room exactly where `applyRoomReorder` puts it (a property test covers every room × slot), which is why the commit itself moves nothing visible.
  - **The drop is aimed by the carried room's leading edge** (`roomDragHitY`: its bottom when carried down, its top when carried up), not by the pointer. The grip sits near the frame's top, so aiming by the pointer meant carrying an expanded room down its own full height — the collapsed room below hidden beneath it the whole way — before anything slid; a release where it *looked* past landed a no-op. Not by the centre either: the carry clamp stops a tall room's centre short of a short end room's, making the first/last slot unreachable. The leading edge reaches every slot within the clamp (a sweep test proves it) and resolves to a no-op at rest.
  - **The settle is a FLIP through the Web Animations API** (`settleInto`, `SETTLE_MS = 150`) over **every** room: each frame's centre is read before the commit, and on the next frame each one that moved animates from there into its new slot — the carried one as `translateY(d) scale(LIFT_SCALE)` → `none` (also after a no-op drop: it still comes down from where it was carried), a passed one as `translateY(d)` → `none`. The second case matters on a quick flick: releasing inside a 180 ms slide removes the transition in the same render as the commit, so the sliding room would otherwise jump the rest of the way. Centre, not top, because the lift scales about the centre. The hook skips the settle under `prefers-reduced-motion`; the CSS slides need no rule of their own, since `base.css`'s global reduced-motion rule already zeroes every transition.
  - **A settle still gliding is landed before the next lift measures** (`Animation.finish()` on every running settle, plus cancelling a not-yet-run settle frame): `getBoundingClientRect` includes a running animation's transform, so grabbing a room within `SETTLE_MS` of a drop would otherwise freeze a moving box into every slot and slide of the new drag.
  - **`LIFT_SCALE` (1.02) must equal the lifted rule's `scale:`** — the settle starts from it, so a mismatch pops on every drop. `useRoomDragReorder.test.tsx` reads `DetailPanel.module.css` and pins the two.
  - **`.roomDragActive` on `.sessionTabStrip`** also gives a drag-wide `cursor: grabbing` by turning `pointer-events` off on every descendant (a cursor on the 24×24 grip alone was gone after a few px, and this silences the session cards' hover tints mid-drag — safe because the gesture listens on `window`), and in the rail locks wheel-scroll with `overflow-y: hidden` (keeps `scrollTop`; a mid-drag scroll would stale the lift-time rects and pull the room off the pointer).
  - **The lifted surface is opaque** — `color-mix(in srgb, var(--room-color) 7%, var(--bg-card))`, with `z-index: 1`, a soft shadow and a room-colour glow. The resting background is 7% room colour over *transparent*, which would show the neighbours' text through a room carried across them. Individual `translate`/`scale` properties (not `transform`) let the scale ease in over 150 ms while the translate tracks the pointer 1:1.
  - **The grip is rail-only** (`isVertical`). In the top bar rooms sit side by side, but `computeRoomInsertIndex` compares Y only, so a drag there could never land where it was released — and vertical slides would break the row. ▲/▼ still reorder there.
  - **Every frame gets a `translate` during a drag, 0px included.** A non-`none` translate makes each frame a stacking context, which keeps its absolutely-positioned decorations — the room label (`z-index: 4`) and its cards' index badges (`z-index: 3`) — inside it. Scoped to the sliding rooms only, the other rooms' labels and badges paint *over* the carried room (`z-index: 1`); confirmed by rendering exactly that mutation.
  - **Known gaps, deliberately out of scope**: other pointers' events are not filtered (a second finger can move the carried room and its `pointerup` commits the drop); a change to the visible room list mid-drag leaves the lift-time rects stale, so the drop can land one slot off the preview; no edge auto-scroll (the wheel lock means a long rail can only reach what is on screen — ▲/▼ still can); no Escape-to-cancel.
  - The queue's own drag (`useQueueDragReorder`) still uses the old fade + caret; the two differ on purpose until it is ported.
- **Kill all sessions in a room**: each room frame carries a **skull icon** (`KillRoomIcon` + `.roomKillToggle`, dim at rest, red on hover/focus) right after the collapse chevron, inside the `.roomHeaderRow`. It renders only when the room has ≥1 **live** session (`roomLiveCount`, computed by counting `room.sessionIds` whose session exists and `status !== 'ended'`), so a room of only ended cards shows no icon. Clicking it `stopPropagation`s (no session-switch) and calls `uiStore.openRoomKill(roomId)`, which sets `roomKillTargetId` + `activeModal = ROOM_KILL_MODAL_ID` (`'room-kill-confirm'`). The lazy-mounted `RoomKillConfirmModal` then lists the live sessions (capped at 8 + "+N more"), and on confirm `Promise.all`s a per-session kill that mirrors `KillConfirmModal` exactly (`POST /api/sessions/:id/kill` → transport-aware terminal close via `closeManagedTerminal`), then toasts a summary (`Terminated N…` / `Terminated K of N… — F survived` / `Failed to kill…`) and deselects if the open session was among the killed. **`roomKillTargetId` is the modal's source of truth** — it kills the room's live sessions regardless of the current room filter, and the icon is a single-click-safe affordance (the modal always confirms). Because room frames are skipped in activity-sort mode, the kill icon is absent there too.
- **Display mode toggle** switches between compact (title-only) and detailed (mini robot face + project + CLI badge) cards (`cardDisplayMode` in uiStore). Alongside it, the **dock toggle** (`navPosition`) docks the session nav as a left rail or back on top, and the **maximize toggle** (`maximized`) hides the session strip entirely for more terminal space.
- **CLI badge** (`getCliBadge`) derives CLAUDE/CODEX/AIDER from the SSH command or `backendType`.
- **Recompute gating (perf)**: the `sessions` Map reference changes on every update (`new Map(...)`). To skip the O(N) sort + room-grouping on unchanged content, SessionSwitcher derives a stable `sessionsSignature` from `sessionId|status|pinned|title|projectName|colorIndex|accentColor|terminalId` (sorted + joined) and keys the heavy memos (`sortedSessions`, `activeSessionIds`, and downstream `filteredSessions`/`tabRenderItems`) to that signature instead of the Map reference. **`lastActivityAt` is appended to the signature only when `sessionSortMode === 'activity'`** — it ticks on every hook event, so including it unconditionally would defeat this gating, while omitting it in activity mode would freeze the list (nothing else in the signature changes when a session merely stays busy, so rows would never reorder).

### SessionControlBar
- **`<SessionControlLock sessionId={…} />` is the bar's FIRST child** — which device is driving this session, ahead of every action that assumes you are. **It renders `null` when `devices.length <= 1`**, so a solo workspace gains no chrome at all. Otherwise it shows exactly one of three states:
  - **(a) Another online device holds it** (`holder.online && holder.clientId !== myId`) → `🔒 Driven by <label>` plus **Ask** (`POST /presence/control/request`, toasts "Asked … to hand over") and **Take control**, which stays **disabled with a live countdown** (`Take in Ns`) until the holder has been idle `IDLE_TAKEOVER_MS = 60_000`. The countdown is derived from `holder.lastActivityAt` against a local 1 s interval that only runs while the lock is on screen — the server has no reason to broadcast once per second, and the actual `claimControl(force)` re-checks the window, so an early click is refused rather than wrongly granted. `now === 0` on the first render (before the effect samples the clock) is treated as "just claimed", so the button starts disabled instead of flashing enabled for a frame.
  - **(b) An incoming hand-over request aimed at us** — `pendingRequests.get(sessionId)` is set *and* we are the holder; `useWebSocket` only files a `control_requested` into the store when `msg.toClientId === getClientId()`, so the broadcast is a no-op on every other device → `🙋 <label> wants control` with **Grant** (`grantControl` → the baton transfers) and a **×** Dismiss that just clears the local request. This branch is checked before (a), so being asked always wins over the spectator view.
  - **(c) We hold it and other devices are connected** → `🎮 You control this` + **Release**, so handing over doesn't make the other device wait out the idle window.
  - **Why it exists:** the write gate is silent by design — without this chip a spectator types into the terminal and *nothing happens*, which reads as a broken app rather than as another device holding the session. `IDLE_TAKEOVER_MS` here mirrors the server constant in `presenceManager.ts`; the two must stay in sync or the button enables before the server will honour it.
- **`⚠ <reason>` interrupted chip** (only while `session.interruption` is set, immediately after the control lock) — `API error` / `rate limit` / `network` via `faultLabel(kind)`, with the raw banner in its `title`. Non-interactive and deliberately styled **against** `.ctrlBtn` (`.ctrlInterrupted`: pill `border-radius: 999px`, no border, `font-weight: 400`, sentence case, `cursor: help`) — it shares this row with KILL/MUTE/ALERT and ALERT is also orange, so matching the button treatment made it read as a fourth, fake-clickable button. No dismiss control: it self-clears on the next forward-progress hook event. See [Auto-Resume Watchdog](./auto-resume-watchdog.md).
- **RESUME** (only when status `ended`) POSTs `/api/sessions/:id/resume`; inflight fetch is aborted on unmount/session change.
- **KILL** opens `KillConfirmModal` (`openModal(KILL_MODAL_ID)`); the modal POSTs `/api/sessions/:id/kill` `{confirm:true}`, uses the response's canonical `terminalId` (falling back only for an older server), then calls `closeManagedTerminal()` (Electron `killPty` for `pty-*`, plus REST registration cleanup), and deselects. The toast distinguishes an isolated PID kill from a managed-terminal close that deliberately leaves a shared Codex host alive; a terminal-less shared-PID thread remains selected and displays the server's safe-rejection message.
- **MUTE/UNMUTE** toggles `session.muted` (`toggleMute` + `muteSession`/`unmuteSession` in alarmEngine).
- **SHARED / HOST ONLY** toggles `session.remoteVisible` (`toggleRemoteVisible`) — **optimistic**: the local store flips (and the button label/tooltip changes) immediately on click, before the fire-and-forget persist resolves; the authoritative gate is server-side in `sessionVisibility.ts` regardless of what this button shows. Absent (`undefined`) reads as HOST ONLY — hidden from every device but this one; SHARED lets other devices on the LAN see, open, and stream this session. See [Session Visibility](../server/session-visibility.md).
- **🛰 AUTO-RELINK / RELINK OFF** toggles `session.remoteControlDaemon` (`toggleRemoteControlDaemon`) — **off by default, opt-in per session**, since enabling it types `/remote-control` slash commands into a live CLI. When ON, an idle session has its Claude Code Remote Control link auto-refreshed (disconnect + reconnect) at most once every 30 minutes so it keeps showing as live in the Claude app. See [Remote Control Daemon](../server/remote-control-daemon.md).
- **ALERT** toggles `session.alerted` (`toggleAlert` + `alertSession`/`unalertSession`) — loud sounds for approval & completion. (Distinct from the dormant `AlertModal`.)
- **Room `<Select>`** moves the session: removes it from any room that currently contains it, then adds it to the chosen room (`''` = No room).

### Modals
- `KillConfirmModal` is lazy-mounted via the `LazyModal` wrapper (only mounts when `activeModal === KILL_MODAL_ID`) to avoid extra Zustand subscriptions during DetailPanel mount.
- `RoomKillConfirmModal` is lazy-mounted the same way (`activeModal === ROOM_KILL_MODAL_ID`). `ROOM_KILL_MODAL_ID` and `roomKillTargetId` live in `uiStore` (not the modal component) so `openRoomKill` can reference the id without a store↔component import cycle; `closeModal` clears both `activeModal` and `roomKillTargetId` so a stale room can't leak into the next open. See the room kill bullet under **SessionSwitcher details**.
- `AlertModal` (timer alert → `db.alerts`) is not currently mounted anywhere; it is documented here as a dormant component.

### Persistence
- Selection: `localStorage['selected-session']`, restored on refresh.
- Nav dock position: `localStorage['nav-position']` (`'top'`/`'left'`), restored on load. Nav-rail folded state: `localStorage['nav-rail-collapsed']` (`'1'`/`'0'`, uiStore `navRailCollapsed`), restored on load (only has a visible effect in left-dock mode). Maximized mode (uiStore `maximized`) is intentionally **not** persisted — it resets to off each load and when the panel closes.
- Visited projects: an **LRU** Map (`visitedProjects`) keeps the `MAX_MOUNTED_PROJECTS = 3` most-recently-visited sessions' `ProjectTabContainer`s mounted; the rest unmount. Ordering and eviction live in [`src/lib/mountedProjectsLru.ts`](../../../src/lib/mountedProjectsLru.ts) (`retainRecentProjects`, `isMostRecentProject`) so they are unit-testable without mounting the panel. On session re-key (e.g. after `/clear`, via `replacesId`) the per-session `agent-manager:project-tabs:session:{id}` and `agent-manager:file-tabs:{id}:{tabId}` localStorage keys are migrated from the old id to the new one. An evicted session re-hydrates its sub-tabs, file tabs and scroll positions from those same localStorage keys on the next visit — only the in-memory file-content cache is re-fetched.
  - **Why it is capped:** each mounted container holds a `react-arborist` file tree, its own file-content cache, rendered markdown, and — for PDFs — an `<iframe>` that costs a whole Chromium `pdf-renderer` helper process. Retaining every visited session grew the renderer past 400 MB of `phys_footprint` over a day of use and left orphaned `pdf-renderer` processes alive.
  - **Never evicted:** the active session, and any session `isProjectEditing()` reports as busy ([`src/lib/projectEditGuard.ts`](../../../src/lib/projectEditGuard.ts)). `ProjectTab`'s markdown draft (`mdDraft`) and new-file buffer (`newFileContent`) are component-local and unpersisted, so unmounting mid-edit would silently discard the user's typing. Pinning may hold the Map above the cap; it shrinks back once those editors save or cancel.
- Close: Escape is a three-step handler — it closes search first, else exits maximized mode, else restores a minimized panel; it does **not** deselect (deselect would apply `display:none` and reset scroll to 0). Escape is ignored when an xterm has focus. The SessionSwitcher "‒" button calls `minimizeDetailPanel` (sets `detailPanelMinimized`), the panel's only non-destructive close gesture; full deselect (`selectedSessionId → null`) happens only on kill (`KillConfirmModal`).
- **Dashboard top-bars auto-hide**: while the panel is in view, `AppLayout` hides **both** the global `<Header>` and `<NavBar>` (`hideTopBars = !!selectedSessionId && !detailPanelMinimized`) so the panel reclaims the full height. Minimizing to a badge or deselecting restores both bars. See [Views & Routing](./views-routing.md) "Top-bars auto-hide".

## Change Risks
- Defining `TerminalContent`/`OpsTerminalContent` inside `DetailPanel` (instead of module scope) remounts the terminal on every render — keep them outside.
- Adding heavy components without lazy mounting (or without the always-mounted-host pattern for terminal/project) degrades performance.
- Changing tab ids/order requires migrating `localStorage['active-tab']` and updating the keyboard-shortcut tab bindings.
- `SessionSwitcher`'s `.switcherIndex` count badge (`DetailPanel.module.css`) referenced `var(--bg-elevated)` — undefined in every theme file, so it always rendered the same hardcoded translucent-white fallback regardless of theme. Fixed to `var(--bg-accent)`, matching `NavBar`'s own `.badge` precedent for a small accent-cyan count pill.
- The two layout modes must stay mutually exclusive — a new mode must clear the others via `turnOff`, or duplicate xterm/project subscriptions appear.
- **Room drag carry preview** (see the SessionSwitcher bullet): moving the per-move carry offset into React state re-renders every session card at pointer rate; putting a `translate` transition on the resting `.sessionTabRoomGroup` (outside `.roomDragActive`) makes every drop bounce; re-measuring rects mid-drag makes the slot flicker; changing the lifted `scale:` without `LIFT_SCALE` makes every drop pop (a test catches that one); rendering the grip in the top bar re-exposes the Y-only hit test to a horizontal row; aiming the hit test by the pointer again (or by the carried centre) brings back the tall-room no-op drops (or unreachable end slots); giving only the sliding frames a `translate` lets other rooms' labels and badges paint over the carried room; measuring at lift without landing a running settle bakes its transform into the whole next drag.
- SessionSwitcher's heavy memos depend on `sessionsSignature`, NOT on `sessions`. If you add a card-display field, include it in the signature or the tab strip won't refresh; re-adding `sessions` to the dep array re-enables the every-update recompute this optimization avoids.
- `AlertModal` is dormant — before relying on it, wire an opener (`openModal(ALERT_MODAL_ID)`) and a render site, or remove it.
- **Removing `SessionControlLock` from the control bar makes the write gate invisible, not absent.** The server still refuses a spectator's keystrokes; the UI would simply stop explaining why, which is indistinguishable from a broken terminal. Its `devices.length <= 1` early return is what keeps a single-device workspace unchanged, so the guard belongs in the component, not at the call site.
- **A tab count badge must never come from the tab's own component state** — NOTES and QUEUE both unmount when you leave them, so a count lifted from `NotesTab`/`QueueTab` would read 0 exactly when it matters (viewing another tab). Keep both counts in stores, and keep DetailTabs' cache-warming effect keyed to `sessionId`.
- **Notes API contract**: a bare snake_case row array on GET, and `DELETE /api/db/notes/:id` (not session-nested). Both were mismatched in `NotesTab` and failed *silently* — the list read empty and deletes 404'd with no error surfaced, since neither call checked `resp.ok`. Any new notes call must check `ok` and go through `notesStore`'s `fromRow` mapping.
- **`NoteMarkdown` must only ever be reached through `lazy()`.** It pulls ~300 kB of react-markdown/remark/rehype, and `NotesTab` is reachable from `DetailPanel`, which sits in the eager entry chunk — the same reason `AiPopupHistory` and `ProjectTabContainer` are lazy. `NotesTab` itself is lazy too, keeping the editor and media helpers off the boot path; the whole rich-notes feature costs **+264 bytes** eager. Only `notesStore` needs to stay eager (DetailTabs reads it for the tab's count badge). Verify with `npm run build` — the entry chunk must contain zero react-markdown references.
- **Never write a bare `.noteBody code { background }` rule.** `.noteBody code` (0-1-1) outranks highlight.js's `.hljs` (0-1-0), so it repaints every fenced block with the inline-code background while hljs's light foreground stays — unreadable on every light theme. The rule is scoped `.noteBody :not(pre) > code` for exactly this reason, and `.noteBody pre code` must not reset `background`/`padding` either.
- Wide content inside a note (fenced code, tables) **must scroll in its own box** — the card sits inside `.tabScroll`, so an unbounded child drags the entire tab sideways. `.noteBody pre` and `.noteTableWrap` both carry `overflow-x: auto; max-width: 100%`.
- **Raising `MAX_MOUNTED_PROJECTS` re-inflates renderer memory** — each extra mounted `ProjectTabContainer` costs a file tree, a file-content cache, and (for any open PDF) a whole `pdf-renderer` process. Conversely, any **new unpersisted state added to `ProjectTab` must be reported through `projectEditGuard`** (or persisted), or LRU eviction will silently discard it — the guard currently covers only `mdDraft` and `newFileContent`.
